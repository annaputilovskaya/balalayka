# AGENTS.md — backend

## 1. Область

Каталог `backend/` содержит Python-приложение, тесты и миграции. Правила этого файла действуют для `backend/app/`, `backend/tests/` и `backend/alembic/`.

- Стек: Python 3.12+, FastAPI, Pydantic v2, SQLAlchemy 2.0 async, Alembic, PostgreSQL 16, Redis/ARQ, MinIO.
- `pyproject.toml` и `poetry.lock` пока лежат в корне и переносятся в `backend/` на этапе 0.
- Frontend-шаблоны и статика живут в `frontend/`; деплой — в `deploy/`. Не добавляй их сюда.
- Источник истины по решениям — `docs/decisions.md`. Перед изменением поведения прочитай ADR-002, ADR-003, ADR-007 и ADR-009.

## 2. Структура

```text
backend/
├── app/
│   ├── core/          # config, db, security, errors, logging, pagination
│   ├── auth/          # регистрация, вход, сессии, CSRF
│   ├── users/         # профили, роли
│   ├── channels/      # каналы, подписки
│   ├── videos/        # метаданные, статусы, upload/complete, streaming
│   ├── media/         # MinIO, presigned POST, ffprobe/ffmpeg
│   ├── engagement/    # лайки, комментарии, просмотры
│   ├── playlists/     # плейлисты и элементы
│   ├── search/        # поиск и read-модели ленты
│   ├── moderation/    # жалобы, скрытие, аудит
│   ├── admin/         # роли и служебные операции
│   ├── web/           # Jinja-роуты и формы
│   ├── api/           # JSON-роуты /api/v1
│   └── workers/       # ARQ worker и задачи обработки
├── tests/
│   ├── unit/
│   ├── integration/
│   └── e2e/
└── alembic/
```

Feature-модуль содержит `router.py`, `api.py`, `service.py`, `repository.py`, `models.py`, `schemas.py`; read-модели — в `queries/`.

## 3. Слои и транзакции

Порядок вызова: `router/api → service → repository → models`. Для чтения: `router/api → queries`.

- `router/api` — тонкий адаптер: разбор запроса, вызов сервиса, формирование ответа. Без SQL и бизнес-логики.
- `service` — use case, проверка прав, границы транзакции.
- `repository` — запись и доменные операции с ORM.
- `queries/` — read-модели с явным SQL/JOIN для ленты, поиска, канала и очереди модерации.
- Одна транзакция на запрос; сервис владеет `commit`/`rollback`.
- Сервис не вызывает другой сервис, который открывает собственную транзакцию.
- Никакого lazy-loading за пределами сервиса; связи загружаются явно.
- Feature-модуль не импортирует ORM-модели другого модуля напрямую — только публичные сервисы и схемы.

## 4. Ошибки и валидация

- Доменные ошибки объявляются в `app/core/errors.py` и транслируются на границе в единый JSON-формат.
- Формат ошибки: машинный `code`, русское `message`, опциональные `details` и `request_id`. Точная схема — в `core/errors.py`.
- Роутеры не ловят `Exception` и не собирают ответы об ошибках вручную.
- Внешние данные валидируются Pydantic v2 на границе; внутри домена — уже доверенные типы.
- Ошибка валидации — `422`; отсутствие аутентификации — `401`; недоступный объект — `404`.
- Не раскрывай стектрейсы, SQL, пути и секреты в ответах.
- Запрещены `except: pass` и проглатывание исключений без логирования и доменной ошибки.

## 5. Права доступа и IDOR

- Каждый сервисный метод, работающий с объектом по ID, проверяет владельца, роль и видимость.
- UI и шаблоны не являются защитой: проверка выполняется в сервисе и в SQL-предикате.
- Приватность — единая `AccessPolicy.can_view_video(viewer, video)` и общий SQL-предикат (ADR-009).
- `private` — только owner и `video_acl`; `unlisted` — по прямой ссылке, но не в списках; `hidden` — `404` для всех, кроме owner/moderator/admin.
- Модератор получает private-видео только в контексте жалобы, с аудитом (ADR-014).
- Чужой объект отдаёт `404`, чтобы не раскрывать существование.
- Любая новая read-поверхность обязана использовать общий фильтр видимости.
- Раздача медиа — только через backend, с проверкой доступа и поддержкой `Range` (ADR-007).

## 6. База данных и миграции

- SQLAlchemy 2.0 async, типизированные модели через `Mapped[]`, `mapped_column`.
- Первичные ключи — UUIDv4; время — `timestamptz` в UTC.
- Soft delete для видео и комментариев; hard delete для лайков.
- Ограничения (`FK`, `unique`, `check`, `not null`) задаются в моделях и миграциях.
- Схема меняется только через Alembic; каждая миграция проверяется на чистой БД.
- `alembic revision --autogenerate` допустим только локально как черновик; в деплое — только `alembic upgrade head`.
- Миграция и модель меняются одним коммитом; ручная правка autogenerate обязательна.
- Расширения (`pg_trgm`) создаются миграцией.
- Параметризованный SQL обязателен; конкатенация пользовательских значений в SQL запрещена.

## 7. Async, конфиг и логи

- В async-коде нет блокирующих вызовов: файлы, сеть и subprocess — через async-API или executor.
- ffmpeg/ffprobe запускаются через `asyncio.create_subprocess_exec` в worker, не в HTTP-запросе.
- Конфиг — только из env через настройки `app/core/config.py`; значения по умолчанию не содержат секретов.
- Секреты, пароли, session-токены и presigned query string не логируются.
- Логи структурированные, с request ID; ошибки логируются один раз на границе.
- Внешние вызовы имеют таймауты; retry — только для идемпотентных операций.
- Сессии — в PostgreSQL, не в Redis; Redis используется для ARQ и rate limit.

## 8. Тесты

- `tests/unit/` — сервисы и политики без HTTP и БД.
- `tests/integration/` — API + PostgreSQL с миграциями; тестовая БД максимально близка к production.
- `tests/e2e/` — критический сценарий «регистрация → загрузка → обработка → просмотр → лайк → комментарий».
- TDD обязателен для бизнес-логики, прав доступа и работы с БД.
- Обязательные тесты: ACL/IDOR на всех read-поверхностях, роли, hide/restore, лимиты и `complete` загрузки, `Range` 206/416, уникальность лайков и подписок, CSRF/401.
- Coverage для сервисов — не ниже 70%; критичные политики — 100% поведения.
- Тест не должен зависеть от порядка запуска и внешнего интернета.

## 9. Команды

Выполняются из `backend/` после переноса конфига (до переноса — из корня).

```bash
poetry install
poetry run ruff check .
poetry run ruff format --check .
poetry run mypy app
poetry run pytest
poetry run alembic upgrade head
```

- `make check` — единая локальная проверка: Ruff, mypy, pytest.
- Перед коммитом обязательны зелёные `make check` и миграция на чистой БД.
- Новые зависимости добавляются через Poetry и фиксируются в `poetry.lock`.

## 10. Готовность backend-изменения

- Сценарий работает через API и через страницу, если это пользовательское действие.
- Права проверены для гостя, владельца, чужого пользователя, модератора и админа.
- Ошибки соответствуют единому формату, логи не содержат секретов.
- Схема БД изменена только миграцией.
- Тесты и линтеры зелёные, `docs/ROADMAP.md` обновлён.
