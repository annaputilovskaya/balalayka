## Правила ведения

- Принятый ADR не переписывается. Изменение решения оформляется новым ADR со статусом `Заменяет ADR-XXX`.
- Каждый ADR содержит: контекст, решение, альтернативы, последствия.
- Статусы: `Предложено`, `Принято`, `Заменено`, `Отклонено`.
- Если решение принято «по умолчанию» и не проверено на практике, это явно указывается в последствиях.
- Ссылки на ADR используются в коде, README и `architecture.md` вместо повторного объяснения причин.

## ADR-001. Границы MVP и non-goals

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Задание требует «копию YouTube, насколько сможете», но срок ограничен 7 днями разработки. Без явных границ проект расползётся, а оцениваются объём, похожесть, архитектура, БД, безопасность и разворачиваемость.

### Решение

В MVP входят:

- 7 экранов: главная, просмотр, канал, поиск, загрузка, вход/регистрация, модерация;
- регистрация и вход по email + паролю;
- роли `user`, `moderator`, `admin`;
- загрузка видео с прогрессом, обработка, превью, статусы;
- каналы, подписки, плейлисты;
- поиск по названию;
- лайки, комментарии, просмотры;
- приватность `public`, `unlisted`, `private`, ACL для private;
- жалобы и скрытие видео;
- Swagger `/docs`, seed демо-данных, деплой одной командой.

P2, если останется время: дизлайки, ответы на комментарии, лента подписок, тёмная тема, жалобы на комментарии.

Вне scope: HLS/ABR, рекомендации, live-стриминг, уведомления, OAuth, email-верификация, сброс пароля, субтитры, несколько каналов на пользователя, i18n, мобильные приложения, видеоредактор, CDN, полнотекстовая релевантность, баны пользователей и апелляции.

### Альтернативы

- **Сделать весь YouTube** — не укладываемся в срок.
- **Только критический путь «регистрация → загрузка → просмотр → лайк → комментарий»** — теряем каналы, поиск, модерацию и приватность, которые явно оцениваются.
- **Только UI-копия без глубины backend** — проваливаем архитектуру, БД и безопасность.

### Последствия

- Появляется фиксированный backlog и возможность сказать «нет» лишним функциям.
- Часть привычных возможностей YouTube осознанно отсутствует; это фиксируется в README.
- P2-функции не блокируют сдачу MVP.

## ADR-002. Модульный монолит

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Одна команда, один деплой, общий домен и ограниченное время. Микросервисы добавили бы сетевые вызовы, распределённые транзакции и эксплуатационную сложность, не давая выигрыша на MVP.

### Решение

Монолит с feature-модулями:

- `backend/app/<feature>/` — `router.py`, `api.py`, `service.py`, `repository.py`, `models.py`, `schemas.py`;
- `backend/app/core/` — конфиг, БД, безопасность, ошибки, логирование;
- backend и worker используют один образ и общий код;
- границы импортов: feature-модуль не импортирует ORM-модели другого модуля напрямую, только публичные сервисы/схемы.

### Альтернативы

- **Микросервисы** — отвергнуты: сеть, транзакции, отдельные деплои и мониторинг.
- **Single-layer MVC** — отвергнут: проверки прав и бизнес-логика расползаются по роутерам.
- **Serverless** — отвергнут: ffmpeg, долгие задачи, cold start и ограничения по времени.

### Последствия

- Простые транзакции и один деплой.
- Риск связности модулей; контролируется import-linter, ревью и запретом кросс-модульных моделей.
- При росте media-worker можно выделить первым.

## ADR-003. Слои, транзакции и read-модели

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Проверки прав и приватности должны находиться в одном месте. Read-запросы ленты, поиска и канала не должны плодить N+1 и дублировать SQL в роутерах.

### Решение

- `router/api` — тонкие адаптеры: разбор запроса, вызов сервиса, формирование ответа.
- `service` — use case, проверка прав, транзакция.
- `repository` — запись и доменные операции.
- `queries/` — read-модели с явным SQL/JOIN для ленты, поиска, канала, очереди модерации.
- Доменные исключения транслируются в единый формат ошибок на границе.
- Одна транзакция на запрос; сервис не вызывает другой сервис, который открывает свою транзакцию.
- Никакого lazy-loading за пределами сервиса.

### Альтернативы

- **Active Record** — отвергнут: бизнес-логика и проверки прав расползаются.
- **Repository для чтения** — отвергнут: борьба с SQL и потеря производительности на JOIN.
- **Полный CQRS/event sourcing** — отвергнут: избыточная сложность для MVP.

### Последствия

- Больше файлов и boilerplate.
- Сервисы тестируются без HTTP.
- Read-модели могут отставать от записи; нужны contract-тесты и единые фильтры видимости.

## ADR-004. Jinja SSR + JSON API

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Нужны 7 экранов, рабочий Swagger `/docs` и простой фронтенд. SPA увеличила бы объём JS и время разработки. Динамические действия (лайк, комментарий, подписка, загрузка, модерация) удобнее делать через JSON.

### Решение

- Страницы рендерятся Jinja2 на сервере.
- Динамические действия идут через `/api/v1`.
- HTML-роуты и JSON API вызывают одни и те же application-сервисы; бизнес-логика в адаптерах запрещена.
- Pydantic-схемы — единый контракт; OpenAPI генерируется FastAPI.
- UI использует cookie-сессию; API принимает ту же сессию как Bearer-токен для Swagger.
- Прогрессивное улучшение: базовые формы работают без JS, динамика — через `fetch`.

### Альтернативы

- **SPA на React/Vue** — отвергнут: время, сборка, дублирование роутинга.
- **API-only + HTMX** — жизнеспособен, но SSR + небольшие JS-модули предсказуемее для 7 экранов.
- **Отдельный BFF** — избыточен для монолита.

### Последствия

- Два адаптера, которые нужно тестировать.
- Swagger с cookie/CSRF требует пояснения в README; для `/docs` используется Bearer-токен.
- Node в runtime не нужен.

## ADR-005. Схема БД, идентификаторы и удаление

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

PostgreSQL обязателен. Нужны связи, приватность, модерация, счётчики и воспроизводимые миграции.

### Решение

- PostgreSQL 16, SQLAlchemy 2.0 async, Alembic.
- UUIDv4 как первичный ключ; публичные идентификаторы не дают перебирать записи.
- Время — `timestamptz` в UTC.
- Soft delete для видео и комментариев; hard delete для лайков.
- Основные сущности:
  - `users`, `sessions`;
  - `channels` — один канал на пользователя, уникальный `handle`;
  - `videos` — `processing_status`, `moderation_status`, `visibility`, метаданные, `views_count`;
  - `video_assets` — `source`, `video_720p`, `thumbnail`, bucket/key/size/content_type;
  - `video_acl` — доступ к private-видео, unique `(video_id, user_id)`;
  - `playlists`, `playlist_items` — порядок и уникальность;
  - `subscriptions` — unique `(subscriber_id, channel_id)`;
  - `likes` — unique `(user_id, video_id)`;
  - `comments` — `parent_id` зарезервирован под P2-ответы;
  - `reports`, `moderation_actions`, `audit_log`.
- Ограничения: FK, check на enum-поля, unique, not null.
- Индексы: `videos(processing_status, visibility, published_at)`, `videos(channel_id)`, trgm по `title`, `comments(video_id, created_at)`, `video_acl(video_id)`, `subscriptions(channel_id)`.
- Миграции только через Alembic; `--autogenerate` не используется в деплое.

### Альтернативы

- **bigint PK** — отвергнут: публичные ID перебираемы, UUID проще для внешних ссылок.
- **Natural keys** — отвергнуты: mutable.
- **NoSQL** — отвергнут: связи, транзакции и модерация требуют реляционной модели.

### Последствия

- UUIDv4 даёт фрагментацию индекса; для MVP это приемлемо.
- Нужна дисциплина миграций и ERD в документации.
- Счётчики (`views_count`, `likes_count`, `comments_count`) денормализованы; reconciliation-джоба позже.

## ADR-006. Object storage и загрузка

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Работа с объектным хранилищем явно оценивается. Нужны прогресс загрузки, валидация файла, защита от переполнения диска и одна команда деплоя. Домен и TLS у проверяющего отсутствуют — есть только IP и HTTP.

### Решение

- MinIO, три приватных бакета:
  - `incoming-videos` — временные загрузки, lifecycle 24 часа;
  - `media` — готовые видео и превью;
  - `raw-videos` — архив исходников для возможного пересчёта.
- Загрузка — **presigned POST** (не PUT) напрямую в `incoming-videos`:
  - ключ строго `videos/{user_id}/{video_id}/source`;
  - `content-length-range`: `1..524288000` (500 МБ);
  - `Content-Type` начинается с `video/`;
  - expiry 15 минут;
  - `success_action_status=201`.
- `POST /api/v1/videos/{id}/complete` — недоверенный клиентский вызов:
  - проверяет владельца и статус `draft`;
  - делает `HEAD` объекта через внутренний MinIO;
  - сверяет размер, тип и ключ;
  - ставит `uploaded`, создаёт job и возвращает `202`;
  - при несоответствии — `422` и удаление объекта.
- Максимальная длительность — 30 минут; проверяется `ffprobe` в worker.
- После успешной обработки исходник переносится в `raw-videos`; при ошибке остаётся в `incoming-videos` для retry.
- MinIO не публикуется наружу. Nginx проксирует только `/incoming-videos/` в MinIO без rewrite пути, с сохранением `Host`, `client_max_body_size 500m` и `proxy_request_buffering off`. Загрузка same-origin, CORS не нужен.
- `PUBLIC_BASE_URL=http://<IP>` используется при подписи presigned POST; host/path должны совпадать с тем, что видит nginx.

### Альтернативы

- **Presigned PUT** — отвергнут: нельзя надёжно задать `content-length-range`; лимит проверялся бы только после загрузки.
- **Backend-mediated upload** — безопаснее и проще, но создаёт трафик и дисковую нагрузку на backend; для 500 МБ и демо допустим, однако выбран прямой POST как более масштабируемый.
- **Публичный bucket для готовых видео** — отвергнут: private и hidden видео утекали бы по прямой ссылке (см. ADR-007).
- **Local filesystem** — отвергнут: ТЗ требует объектное хранилище.

### Последствия

- Нужно проверить SigV4 через nginx на чистой VM; это входит в deploy smoke.
- Presigned URL не логируется с query string.
- Брошенные загрузки удаляются lifecycle-правилом; `complete` идемпотентен.
- Один пользователь не должен иметь много одновременных загрузок; нужен rate limit.

## ADR-007. Раздача медиа и приватность

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Private-видео должны быть доступны только владельцу и явно разрешённым пользователям. Скрытое модератором видео не должно оставаться доступным по прямой ссылке. При этом нужен `Range` для перемотки и превью.

### Решение

- Все готовые медиа лежат в приватном бакете `media`.
- Раздача — через backend:
  - `GET /media/videos/{id}` — video stream с `Range`, 206/416;
  - `GET /media/thumbnails/{id}` — превью.
- Проверка доступа на каждый запрос:
  - `public` — без авторизации;
  - `unlisted` — без авторизации по прямой ссылке, но не в лентах/поиске/канале;
  - `private` — owner + `video_acl`;
  - `hidden` — 404 для всех, кроме owner/moderator/admin с аудитом.
- Unauthorized всегда получает `404`, чтобы не раскрывать существование видео.
- `Cache-Control`: public/unlisted — `public, max-age=60`; private — `private, no-store`; hidden — `no-store`.
- Nginx-кэш в MVP не включается, чтобы скрытие работало сразу.
- Presigned GET для private не выдаётся. MinIO наружу не публикуется.

### Альтернативы

- **Presigned GET для всех** — отвергнут: URL — bearer-токен, делится, попадает в логи и историю, не отзывается до expiry.
- **Публичный bucket для public/unlisted** — отвергнут: hidden-видео остаётся доступным по прямой ссылке; private требует отдельного bucket и перемещений.
- **Раздельные `media-public` и `media-private`** — жизнеспособно, но добавляет копирование при смене видимости и окно рассинхронизации.
- **Nginx `auth_request` + internal proxy** — правильнее для масштаба, но сложнее с подписью MinIO; отложено.

### Последствия

- Трафик видео идёт через backend; для демо и 720p это приемлемо.
- Смена видимости и скрытие работают мгновенно, без перемещения объектов.
- Нужны тесты `Range`, ACL и поведения hidden.
- При росте — nginx-кэш публичных ответов или отдельный delivery-слой.

## ADR-008. Очередь обработки видео

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

ffmpeg — долгая задача, которую нельзя выполнять в HTTP-запросе. Нужны статусы, ретраи, идемпотентность и защита от потери задачи. Redis уже нужен для ARQ; сессии решено хранить в PostgreSQL.

### Решение

- Очередь: **ARQ + Redis**; Redis с `appendonly yes`.
- Сессии — в PostgreSQL, не в Redis.
- Статусы обработки: `draft → uploaded → processing → ready | rejected`.
- Модерация — отдельное поле `moderation_status` (`visible | hidden`), не смешивается с обработкой.
- После коммита видео backend ставит ARQ-job с `_job_id = video:{id}:process`.
- Reconciler раз в 60 секунд ищет `uploaded` старше N минут и повторно ставит job. Это компенсирует dual-write между PostgreSQL и Redis.
- `max_tries=3`, экспоненциальный backoff, timeout ffmpeg 45 минут.
- Worker запускает ffmpeg через `asyncio.create_subprocess_exec`, без блокировки event loop:
  - `ffprobe` — проверка длительности ≤ 30 минут и наличия видеопотока;
  - H.264/AAC MP4 720p, `+faststart`;
  - превью на 1-й секунде;
  - результат — в `media`, исходник — в `raw-videos` после успеха;
  - при ошибке — `rejected` с причиной, исходник остаётся для retry.
- Worker работает non-root, с ограниченным временем и без доступа к интернету; конкуренция — 1 job на инстанс.

### Альтернативы

- **PostgreSQL queue (`FOR UPDATE SKIP LOCKED`)** — проще и атомарнее, но выбран ARQ из-за уже принятого Redis и удобства очереди; dual-write компенсируется reconciler.
- **Celery** — тяжелее, лишние зависимости.
- **Синхронная обработка в запросе** — таймауты и плохой UX.

### Последствия

- Redis становится обязательным сервисом; при его падении загрузка принимается, но обработка ждёт восстановления.
- Нужен мониторинг длины очереди и failed jobs.
- Reconciler и идемпотентный job id обязательны; без них возможны потерянные задачи.
- Один worker достаточен для MVP; масштабирование — репликами.

## ADR-009. Модель приватности

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

ТЗ требует: private-видео доступно только тем, кому разрешил владелец. При этом нужна YouTube-похожесть, а значит `unlisted` и приватные плейлисты. Утечка возможна через любую read-поверхность: ленту, поиск, канал, плейлист, превью, API, прямой стрим.

### Решение

- `videos.visibility`: `public | unlisted | private`.
- `video_acl(video_id, user_id)` — только для private; unique пара.
- Владелец всегда имеет доступ; доступ выдаётся и отзывается по handle, хранится `user_id`.
- Единая `AccessPolicy.can_view_video(viewer, video)` и SQL-предикат для всех чтений.
- `public` — в лентах, поиске, канале, плейлистах.
- `unlisted` — по прямой ссылке, но исключён из лент, поиска, канала и публичных плейлистов.
- `private` — только owner и ACL; не появляется в чужих списках.
- `hidden` — 404 для всех, кроме owner/moderator/admin; модератор получает доступ только через жалобу.
- Приватные плейлисты видны только владельцу; публичные плейлисты фильтруют недоступные видео.
- Unauthorized → `404`, не `403`.

### Альтернативы

- **Только ACL без visibility** — отвергнут: нет public/unlisted.
- **Per-video secret token** — отвергнут: управление, отзыв и UX хуже ACL.
- **Приватность на уровне канала** — отвергнута: ТЗ говорит про видео.

### Последствия

- Больше состояний и тестов.
- Каждый read-запрос обязан применять фильтр; это проверяется тестами.
- Модераторы и админы не получают свободный доступ к private; только по жалобе/инциденту с аудитом.

## ADR-010. Аутентификация, сессии и роли

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Нужны регистрация/вход, роли, безопасность и рабочий Swagger. Внешний IdP и email-инфраструктура отсутствуют.

### Решение

- Пароли — Argon2id; минимальная длина 8; rate limit на login/register.
- Сессии — в PostgreSQL:
  - opaque token, в БД хранится hash;
  - expiry и ротация при login;
  - cookie `HttpOnly`, `SameSite=Lax`, `Secure` из env;
  - logout и logout-all.
- CSRF: double-submit token + проверка `Origin` для cookie-запросов.
- API принимает либо cookie + CSRF, либо `Authorization: Bearer <session-token>`; второй вариант нужен для Swagger, чтобы `/docs` был рабочим.
- Роли: `user`, `moderator`, `admin`; проверка в сервисе, не в шаблоне.
- Админ создаётся CLI-скриптом; demo-админ создаётся seed с известным паролем и предупреждением в README.
- Модератор скрывает/восстанавливает видео; баны и апелляции вне scope.
- Админ управляет ролями; self-escalation запрещён; изменения ролей аудируются.
- Redis используется для rate limit; сессии от Redis не зависят.

### Альтернативы

- **JWT access + refresh** — отвергнут: revocation и rotation сложнее.
- **Redis-сессии** — отвергнуты: flush/eviction выкидывает всех; PG-сессии надёжнее для демо.
- **OAuth / email-верификация** — вне scope.

### Последствия

- Запрос к БД на проверку сессии; для MVP нормально.
- CSRF-обвязка для форм и fetch.
- Для HTTP по IP `SESSION_COOKIE_SECURE=false`; это осознанный компромисс, отмеченный в README.
- Bearer-токен в Swagger — та же сессия; expiry и отзыв общие.

## ADR-011. Frontend и похожесть на YouTube

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Дизайн и расположение элементов оцениваются. Фронтенд должен быть простым, без SPA-инфраструктуры.

### Решение

- Jinja2 + precompiled Tailwind CSS + vanilla ES-модули.
- CSS собирается заранее и коммитится; Node не нужен в runtime.
- Чеклист похожести:
  - topbar с логотипом, поиском, загрузкой и аватаром;
  - sidebar с навигацией;
  - сетка превью с длительностью, каналом, просмотрами и датой;
  - watch-страница: плеер, заголовок, канал, подписка, лайк, описание, комментарии;
  - channel-страница: баннер, вкладки «Видео» и «Плейлисты», подписка;
  - search results;
  - upload с drag-and-drop и прогрессом;
  - moderation с очередью жалоб и действиями.
- Светлая тема по умолчанию; тёмная — P2.
- Никаких inline-стилей и inline-обработчиков; CSP.
- Русский UI, английские идентификаторы.

### Альтернативы

- **Tailwind CDN** — отвергнут: offline/CSP.
- **SPA React** — отвергнут: время и сборка.
- **Plain CSS** — жизнеспособен, но медленнее в достижении похожести.

### Последствия

- Нужен dev-build CSS и риск drift; проверяется screenshot-review.
- Node не нужен в runtime.
- CSP требует дисциплины: внешние скрипты и inline-код запрещены.

## ADR-012. Поиск и пагинация

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Поиск по названию, лента и канал должны работать на небольших объёмах без Elasticsearch.

### Решение

- PostgreSQL `pg_trgm` + GIN-индекс по `title`; дополнительно ищем по имени канала.
- `ILIKE`-ранжирование; для MVP достаточно.
- Keyset-пагинация `(published_at, id)` для ленты, поиска и канала.
- Фильтры: `processing_status='ready'`, `moderation_status='visible'`, visibility по правилам ADR-009.
- `unlisted`, `private`, `hidden` исключены из поиска и лент.

### Альтернативы

- **`tsvector`** — лучше релевантность, хуже частичные слова; можно добавить позже.
- **Elasticsearch** — отвергнут: лишний сервис и ops.
- **Offset-пагинация** — отвергнута: глубокие страницы и нестабильность.

### Последствия

- Нужно `CREATE EXTENSION pg_trgm` в миграции.
- Индекс занимает место и замедляет запись; для MVP приемлемо.
- Релевантность простая; сложные запросы не поддерживаются.

## ADR-013. Деплой и эксплуатация

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Проверяющий даёт чистую Ubuntu 22.04/24.04 и IP; домена и TLS нет. Всё должно подняться одной командой, включая БД, хранилище и фоновую обработку.

### Решение

- `deploy/deploy.sh` — идемпотентный:
  - проверяет/устанавливает Docker и Compose plugin;
  - один раз генерирует `.env` с паролями и `SECRET_KEY`;
  - ставит `PUBLIC_BASE_URL=http://<IP>` и `SESSION_COOKIE_SECURE=false`;
  - поднимает compose с healthchecks;
  - прогоняет миграции, создаёт бакеты и пользователя MinIO, выполняет seed.
- Сервисы compose: `nginx`, `backend`, `worker`, `postgres`, `redis`, `minio`, `minio-init`.
- Наружу открыт только nginx:80. Postgres, Redis и MinIO — internal.
- MinIO console отключён; root-доступ не публикуется.
- Nginx проксирует `/incoming-videos/` в MinIO для presigned POST; `/media/` — в backend.
- Healthchecks: `pg_isready`, `redis-cli ping`, MinIO health, backend `/healthz`.
- `restart: unless-stopped`; structured logs; request ID.
- Seed идемпотентен; демо-пользователи, роли, видео, комментарии и плейлисты создаются один раз.
- TLS/домен — опциональный Caddy-профиль на будущее; в основном сценарии HTTP по IP.

### Альтернативы

- **Caddy по умолчанию** — проще TLS, но нужен домен; у проверяющего его нет.
- **Kubernetes** — overkill.
- **Bare metal без Docker** — невоспроизводимо.
- **Публичный MinIO port** — отвергнут: лишняя поверхность атаки.

### Последствия

- HTTP без TLS: пароли и сессии идут в открытом виде; это допустимо только для проверки, о чём сказано в README.
- Одна VM, без HA и бэкапов.
- Скрипт должен переживать повторный запуск и не перетирать данные.
- Нужен запас диска под `raw-videos` и `media`.

## ADR-014. Модерация и аудит

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

ТЗ требует жалобы и скрытие видео. Роли и безопасность оцениваются; действия модераторов должны быть проверяемы.

### Решение

- `reports`: target — только видео; причина, комментарий, статус `open/resolved/rejected`, автор, резолвер.
- Очередь модератора: список открытых жалоб, просмотр видео, hide/restore.
- `videos.moderation_status`: `visible | hidden`; скрытие не меняет `processing_status`.
- Скрытое видео: 404 для публики; owner видит статус; moderator/admin — с аудитом.
- Модератор видит private-видео только если на него есть жалоба.
- Append-only `audit_log`: actor, action, target, reason, timestamp, request ID.
- Проверка роли — в сервисе; UI скрывает кнопки, но не является защитой.
- Rate limit на создание жалоб.

### Альтернативы

- **Только админ-удаление** — отвергнут: нет workflow жалоб.
- **Внешняя модерация** — вне scope.
- **Soft delete без аудита** — отвергнут: нельзя доказать действия.

### Последствия

- Дополнительные таблицы и экран.
- В аудите могут быть PII; доступ к нему ограничен.
- Апелляции и баны пользователей — P2/вне scope.

## ADR-015. Тестовая стратегия

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

Автотесты и безопасность оцениваются. Критический сценарий должен проверяться после деплоя, а приватность — на всех поверхностях.

### Решение

- `backend/tests/unit/` — сервисы и политики без HTTP.
- `backend/tests/integration/` — API + PostgreSQL с миграциями; тестовая БД поднимается через Docker/testcontainers.
- `backend/tests/e2e/` — один сценарий: регистрация → загрузка → обработка → просмотр → лайк → комментарий.
- Обязательные тесты:
  - private/unlisted/hidden ACL и IDOR на всех read-поверхностях;
  - роли и модерация;
  - лимиты загрузки и `complete`;
  - Range 206/416;
  - уникальность лайков и подписок;
  - CSRF/401.
- `make check`: Ruff, mypy (pragmatic), pytest.
- Coverage-цель — 70% для сервисов; критичные политики — 100% поведения.
- CI опционален; локальный `make check` обязателен перед коммитом.

### Альтернативы

- **SQLite для тестов** — отвергнут: различия с PostgreSQL.
- **Без e2e** — риск, что деплой-сценарий не работает.
- **Полный browser-E2E на каждый экран** — избыточно для 7 дней.

### Последствия

- Тесты медленнее из-за PostgreSQL.
- Нужны фикстуры и seed для e2e.
- Деплой-скрипт дополняется smoke-проверкой.

## ADR-016. Передача AI-артефактов

- **Статус:** Принято
- **Дата:** 2026-11-06

### Контекст

ТЗ требует сдавать промпты вместе с кодом. Пользователь ведёт ИИ-обвязку самостоятельно и принял решение не хранить промпты в репозитории; вместо этого к архиву прикладывается экспорт сессии OpenCode.

### Решение

- Промпты и служебные материалы ИИ в git не добавляются; `ai-docs/` остаётся в `.gitignore`.
- В README добавляется раздел «AI artifacts», где указано, что экспорт сессии приложен к архиву проекта.
- В экспорте не должно быть секретов, паролей и токенов; пользователь проверяет это перед сдачей.
- Репозиторий остаётся чистым от AI-мусора; воспроизводимость кода от экспорта не зависит.

### Альтернативы

- **Хранить промпты в `docs/prompts/`** — отклонено пользователем: обвязка вне задачи и ведётся отдельно.
- **Хранить в `ai-docs/` и игнорировать** — не попадает в git, но и не является поставкой.
- **Не передавать артефакты** — формально не закрывает требование ТЗ.

### Последствия

- Проверяющий должен найти экспорт в архиве; README обязан явно указать путь/имя.
- Риск забыть приложить экспорт; это пункт чеклиста сдачи.
- Секреты в промптах запрещены.
