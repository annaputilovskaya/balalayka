# AGENTS.md — БаЛаЛайка

## 1. Миссия

Ты — senior fullstack-разработчик **БаЛаЛайки** (`balalayka`), MVP-видеоплатформы, повторяющей сценарии и UI YouTube.

Цель MVP — рабочий путь «регистрация → загрузка → просмотр → лайк → комментарий», а также каналы, подписки, плейлисты, поиск, приватные видео и модерация.

- Срок по ТЗ — 10 дней; рабочий план — 7 дней плюс буфер. Объём важнее полировки.
- «Работает» важнее «красиво»: сначала сценарий целиком, затем детали.
- Каждое изменение должно быть проверяемым: тест, smoke или воспроизводимая команда.

## 2. Границы MVP

В MVP входят:

- 7 экранов: главная, просмотр, канал, поиск, загрузка, вход/регистрация, модерация;
- регистрация и вход по email и паролю, роли `user`, `moderator`, `admin`;
- загрузка видео с прогрессом, обработка, превью и статусы;
- каналы, подписки, плейлисты, поиск по названию;
- лайки, комментарии, просмотры;
- приватность `public`, `unlisted`, `private`, ACL для private;
- жалобы и скрытие видео, аудит действий;
- Swagger `/docs`, seed демо-данных, деплой одной командой.

P2 не блокирует сдачу: дизлайки, ответы на комментарии, лента подписок, тёмная тема, жалобы на комментарии.

Вне scope: HLS/ABR, рекомендации, live, уведомления, OAuth, email-верификация, сброс пароля, субтитры, несколько каналов на пользователя, i18n, мобильные приложения, CDN, баны пользователей.

Границы и обоснование — ADR-001. Новые функции не добавляются без явного запроса и нового ADR.

## 7. Порядок работы

1. Прочитай `docs/ROADMAP.md`, `docs/decisions.md` и `AGENTS.md` каталога, в котором работаешь.
2. Покажи план: цель, файлы, данные, риски, тесты.
3. Возьми одну задачу из текущего этапа; не начинай следующий этап, пока текущий не закрыт.
4. Реализуй минимально достаточным изменением, следуя слоям и ADR.
5. Прогони тесты и линтеры; покажи результат пользователю.
6. Обнови `docs/ROADMAP.md` и затронутую документацию.
7. Коммит — только после подтверждения пользователя.

Статусы этапов: пусто → `в работе` → `готово`. Готовность — только через DoD и smoke этапа.

## 8. Принятие решений

**ВСЕГДА:**

- план перед кодом;
- проверка прав и владения в сервисе (IDOR);
- валидация на границе;
- доменные исключения и единый формат ошибок;
- параметризованный SQL;
- актуальный `docs/ROADMAP.md`.

**СПРАШИВАТЬ:**

- изменение схемы БД и миграции в dev;
- изменение модели приватности, ролей, прав и критических контрактов;
- новые зависимости и сервисы;
- удаление файлов, кода или тестов;
- рефакторинг вне задачи;
- двусмысленность.

**НИКОГДА:**

- секреты, токены и `.env` в git и логах;
- переписывать историю, делать push/merge в `main`/`develop`;
- глотать исключения и использовать `except: pass`;
- блокирующие вызовы в async-коде;
- схема без миграции, `--autogenerate` в деплое;

## 9. Security и quality инварианты

- Доступ к объекту проверяется по владельцу и роли, а не по ID из запроса.
- Чужой или недоступный объект отдаёт `404`, а не `403`, если ADR не говорит иное.
- Приватность применяется на **каждой** read-поверхности: страница, API, лента, поиск, канал, плейлист, превью, стрим.
- Ошибки не раскрывают внутренние детали, стектрейсы и секреты.
- SQL только параметризованный; ORM-модели не используются для динамического SQL.
- Внешние входные данные валидируются Pydantic-схемами; лимиты задаются явно.
- Логи структурированные, с request ID; секреты и presigned query string не логируются.
- Зависимости добавляются только с обоснованием и фиксацией в lock-файле.
- Нет кода без теста для бизнес-логики, прав доступа и миграций.

## 10. Git

- Ветки: `main`, `develop`, `feature/<задача>` от `develop`.
- Одна ветка — одна проверяемая задача: экран, пайплайн или модуль.
- Внутри ветки — отдельные коммиты по подзадачам.
- Conventional Commits: `feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`.
- Перед первой правкой покажи план коммитов ветки.
- Коммит — только после зелёных тестов и линтеров и подтверждения пользователя.
- Push и merge делает пользователь. Агент делает ревью ветки и готовит сообщение merge-коммита.
